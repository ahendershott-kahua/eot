Pod Execution Model

How pods ship working software as fast as possible

02

Why Pods Exist

Pods compress delivery from months to weeks by replacing spec-driven work with prototype-first iteration.

  • Small cross-functional strike teams
  • Prototype first, not spec first
  • Collapse roles, remove translation layers
  • AI fills the gaps that used to require more people
Calendar ships fast. That proves the model. Then it spreads.

Continuous Iteration

Every delivery strengthens the next. The system learns as it runs.

01 Discover
Synthesize stakeholder signals, system context, and competitive inputs to define a differentiated solution direction.
Deliverable: Signed-off PRD + prompt package
02 Iterate
Iterate through working Canvas-driven prototypes with same-day feedback and pre-code stakeholder alignment. Then build, integrate, and continuously test against acceptance criteria.
Deliverable: Validated prototype + working build in staging
03 Launch
Ship to production users, run retrospective, capture learnings, and feed evidence back into the next Discover cycle.
Deliverable: Release + retro intelligence report
Execution becomes predictable when learning never stops.

05

Inputs Replace Deliverables

The old model passed documents between roles. The new model uses AI to generate working inputs into a shared prototype.

The Old Way

  • PM writes PRD over days, hands to Design
  • Designer spends weeks in Figma, hands to Eng
  • Engineer builds from spec, hands to QA
  • Each step adds weeks and loses context

The New Way: Roles Collapse

  • Anyone with VS Code + an approved model (Opus 4.6, Codex, Claude 5.4) can draft, design, or build
  • PM drafts the problem frame AND builds a clickable prototype
  • Designer drafts the PRD AND ships working HTML
  • Engineer scaffolds the app while QA agents, kAutomate, and automation generate structured validation coverage
  • No handoffs. Everyone contributes everywhere.
AI is why 3 people can do what 10 used to. The next four slides show exactly how.

09

QA & Leadership Inputs

QA is not a phase. It starts when the first prototype exists. Leadership removes friction, not approves output.

Embedded from Day 1

  • QA joins at pod kickoff, not after engineering is "done"
  • Tests the first prototype on day 1. Shapes requirements through what breaks
  • Validate on prototypes, not specifications. Bugs caught in context, not after handoff
  • QA supports pods, doesn't gate releases
  • Uses AI to generate test scenarios, edge cases, and regression checklists from the evolving prototype
ChatGPT VS Code

Everyone is QA

  • PM validates assumptions against real user behavior, not specs
  • Designer tests interactions in the working prototype, not in Figma comments
  • Engineer uses AI to generate automated tests alongside every feature
VS Code Opus 4.6

Leadership Unblocks

  • Strategic framing: why this matters right now
  • Fast yes/no on scope questions. No committees
  • Remove organizational friction. Clear the path so the pod can ship
There is no "hand off to QA." QA is already there. Everyone tests. Leadership clears the path.
10

Artifact Expectations

Every artifact should accelerate testing or iteration. If it doesn't, cut it.

What Pods Produce

  • 1-page MVP PRD (problem, scope, done definition)
  • Clickable prototypes (not static mockups)
  • AI-generated test checklists and edge cases
  • Working weekly demo for stakeholder feedback
  • Short decision notes ("we chose X because Y")

What Pods Don't Produce

  • Multi-page spec documents
  • Polished Figma handoff files
  • Status decks or approval presentations
  • Documentation before the thing works
  • Anything that requires a meeting to review
The artifact is the prototype. Everything else is a note that helps the prototype get better.
11

Iteration Speed

Continuous operational progress beats delayed polish.

  • Visible progress: The working prototype advances continuously
  • Stakeholder reaction: Feedback happens inside the real system, not in review meetings
  • Cross-pod learning: Successful patterns spread immediately across teams
Execution is the strategy. The pod that ships fastest teaches the org the most.
12

Definition of Done

Done means operational, testable, usable. Not polished, finalized, documented.

Done Means

  • Operational: works end to end
  • Testable: someone can try it
  • Adoptable: user completes the core flow
  • Demonstrable: showable in a working demo

Done Does Not Mean

  • Pixel perfect
  • Fully documented
  • All edge cases handled
  • Production hardened
Pods ship capability, not perfection.

"Teams no longer operate around a PRD.
They operate around a Prototype."
